# Phase 0 — Software Requirements Specification (SRS)

**Product:** Ariba Shield WAF — Centralized Enterprise Web Application Firewall
**Scope:** Release 0.1 (Lab) — reverse proxy, central management, bilingual UI shell, safe config lifecycle
**Document status:** Draft v0.1
**Source of control:** `enterprise_waf_development_master_plan.md` — this document is the day-to-day development contract and must never contradict the master plan without an approved ADR.

---

## 1. Purpose and scope

This SRS defines the functional and non-functional requirements for **Release 0.1 (Lab)** of Ariba Shield WAF, and anchors the threat model, data model v0, API v0, UI specification, and the sprint backlog used to build it.

### 1.1 In scope for Release 0.1

- Single Linux-node lab deployment (control plane + gateway on one server).
- HTTPS reverse proxy with virtual servers and backend pools.
- Active/passive health checks.
- Request ID and structured access logging.
- Basic admin authentication.
- Application CRUD.
- English/Bangla shell UI with an extensible i18n system.
- Safe configuration validation and atomic last-known-good reload.

### 1.2 Explicitly out of scope for Release 0.1

- Any blocking/enforcement WAF action (Release 0.1 is proxy + management only).
- Signature engine and OWASP CRS integration (Phase 2).
- Multi-gateway management, HA, mTLS bundle distribution (Phase 4).
- Rate limiting, IP lists, bot defense, API protection, learning.
- Custom TLS implementation or cryptography — always use maintained system libraries.
- L3/L4 volumetric DDoS mitigation.
- Any production blocking posture.

## 2. Actors and roles

### 2.1 Actor definitions

| Actor | Description |
|---|---|
| Platform Admin | Manages system settings, reference environment, gateway lifecycle. |
| Security Admin | Manages policies and (later) signatures; in Release 0.1 manages virtual servers and app exposure. |
| App Owner | Manages applications, backend pools, and health checks for owned applications. |
| SOC Analyst | Views traffic, security events, and health; no configuration write access in Release 0.1. |
| Auditor | Read-only access to configuration and audit log. |
| Read Only | Read-only access to all views except audit log. |
| Unauthenticated Browser | Cannot access any management function; the control plane is never on the public traffic path. |

| Capability | Platform Admin | Security Admin | App Owner | SOC Analyst | Auditor | Read Only |

## 5. Use cases and acceptance criteria

### UC-1: Install the lab platform
**Precondition:** Ubuntu Server LTS host, Docker installed.
**Flow:** Run installer → credentials generated and shown once → control plane and gateway start → health endpoint reports ready.
**Acceptance:** Browser can reach the console on the management network; gateway proxies a test app over HTTPS; no default credentials exist.

### UC-2: Create and serve an application
**Precondition:** Authenticated Platform Admin.
**Flow:** Create application → create backend pool with one test node → attach virtual server with TLS → validate and activate config.
**Acceptance:** HTTPS request to the virtual server reaches the backend; response returns within p99 budget; backend node shown healthy in console and metrics.

### UC-3: Modify config with invalid input
**Precondition:** An active virtual server exists.
**Flow:** Submit a config with a semantic error (e.g., duplicate listener) → validation rejects it.
**Acceptance:** The active listener keeps serving; audit log records the rejected attempt; no partial activation.

### UC-4: Simulate gateway reload failure
**Precondition:** Active config vN.
**Flow:** Introduce a configuration that fails at reload → restart the gateway.
**Acceptance:** The gateway restores config vN (last-known-good) automatically and resumes serving; logs document the fallback.

### UC-5: Backend total failure
**Precondition:** Pool with all nodes marked unhealthy.
**Flow:** Send request to virtual server.
**Acceptance:** Client receives a controlled maintenance/503 response; gateway stays up; request ID present.

### UC-6: Bilingual UI
**Precondition:** Authenticated user.
**Flow:** Change profile language to Bangla.
**Acceptance:** UI strings render in Bangla; machine-readable event/status codes unchanged; no missing-key errors.

### UC-7: Audit log
**Precondition:** Auditor role user.
**Flow:** Perform and view mutations (create app, edit pool).
**Acceptance:** Every mutation appears with actor, timestamp, resource, and request ID; Auditor can view; Read Only cannot.

## 6. Data model v0

Public identifiers: ULID. Numeric internal keys only where necessary.

### 6.1 Core tables

| Table | Key fields |
|---|---|
| `organizations` | id, name, created_at |
| `users` | id, organization_id, email, password_hash, language, totp_enabled, status |
| `groups` | id, name, organization_id |
| `roles` | id, name, permissions[] |
| `user_group_memberships` | user_id, group_id |
| `sessions` | id, user_id, token_hash, expires_at, created_at, request_id |
| `audit_events` | id, organization_id, actor_user_id, action, resource_type, resource_id, before_ref, after_ref, ip, request_id, created_at |
| `applications` | id, organization_id, name, description, owner_user_id, status |
| `virtual_servers` | id, organization_id, name, listen_addr, listen_port, tls_enabled, cert_ref, default_backend_pool_id |
| `routes` | id, virtual_server_id, path, backend_pool_id, priority |
| `backend_pools` | id, organization_id, application_id, name, lb_algorithm, health_monitor_id |
| `backend_nodes` | id, pool_id, host, port, weight, active, last_health_state |
| `health_monitors` | id, pool_id, type (tcp/http), interval_ms, timeout_ms, fail_threshold, pass_threshold, http_path, http_expected_status |
| `config_versions` | id, organization_id, version, bundle_hash, status (draft/active/superseded), created_by, created_at |
| `config_deployments` | id, config_version_id, target (gateway), status (validating/approved/activated/failed), error, applied_hash, deployed_at |

### 6.2 Conventions

- All write tables carry `created_at`, `updated_at`, and a `version` column for optimistic concurrency.
- `config_versions` stores the immutable declarative config blob plus its hash; gateways report applied hash and validation errors.
- Audit and session data are append-mostly; session tokens stored as hashes only.

## 8. Deployment topology (Release 0.1)

```text
[Admin Browser] --HTTPS--> [Control Plane (Next.js + Go API)] --PATCH--> [PostgreSQL]   (management network)
                                   |
                                   | generated+validated config (bundle hash)
                                   v
[Client] --HTTPS--> [OpenResty Gateway] --> [Backend Pool A] / [Backend Pool B]
                         |
                         +---> structured JSON logs --> stdout/Prometheus
```

- Single host: all services on the management network; gateway listens on the service-facing interface.
- Control plane is **never** in the traffic path (master plan §3.2).
- Gateway keeps a locally cached last-known-good config for restart recovery.
- Logs/metrics go to stdout + OpenTelemetry collector; Wazuh/SIEM integration arrives in Phase 2.

## 9. Threat model (Release 0.1, STRIDE-style)

### 9.1 Trust boundaries

1. Public internet → gateway (untrusted).
2. Gateway → backend (trusted network, sanitized requests).
3. Admin browser → control plane (management network, authenticated).
4. Control plane → PostgreSQL (trusted internal).
5. Process boundaries: gateway / control API / web console / database.

### 9.2 Key threats and mitigations

| # | Threat | Stride | Mitigation (Release 0.1) |
|---|---|---|---|
| T1 | HTTP request smuggling via conflicting CL/TE | Spoofing/Tampering | Strict parser rejects ambiguous framing; conformance tests; single parse path (rule 1). |
| T2 | Unauthorized control-plane access | Spoofing | HTTPS-only, management binding, generated credentials, no default passwords. |
| T3 | Session hijacking/fixation | Spoofing | HTTP-only/Secure/SameSite cookies, session rotation, short expiry. |
| T4 | CSRF on management API | Tampering | CSRF token + SameSite; idempotency keys; method enforcement. |
| T5 | Log injection / log poisoning | Tampering | Structured JSON, no raw user-controlled multi-line freeform in log fields; log write never blocks traffic. |
| T6 | Config tampering / partial activation | Tampering | Declarative versioned config, bundle hash, validate→stage→atomic switch, last-known-good restore. |
| T7 | Backend info disclosure via error pages | Information disclosure | Controlled 503 page; no stack traces in production responses. |
| T8 | Resource exhaustion (oversized requests) | DoS | Request line/header/body size limits with safe defaults. |
| T9 | Unauthorized audit log tampering | Repudiation | Append-only audit with immutable events; Auditor read-only role. |
| T10 | Secrets exposure | Information disclosure | No bodies/cookies/credentials in logs; envelope encryption for stored secrets. |
| T11 | SSRF via host/header manipulation to backend | Spoofing | Gateway itself sets trusted proxy headers; backends contacted via config-defined nodes only; upstream host header pinned. |

### 9.3 Data classification

| Data | Class | Notes |
|---|---|---|
| Config blobs, TLS cert references | Confidential | Never logged fully |
| Audit events | Confidential | Append-only |
| Access logs (without bodies/cookies) | Internal | 30-day default retention |
| Traffic payloads | Sensitive | Not stored in Release 0.1 |

## 11. Definition of done and release gates

Every Release 0.1 feature must have:
- Approved ADR where architecture changes.
- Threat analysis (from §9).
- Unit + integration tests, negative/error-path tests.
- Permissions and tenant-isolation tests.
- Metrics + structured logs; audit coverage for mutations.
- English + Bangla labels; CI translation checks.
- API + operator documentation; upgrade/rollback consideration.
- Performance impact measured where it touches traffic.
- Security review.

**Release 0.1 cannot ship unless:**
- All critical parser/security tests pass.
- Upgrade and rollback pass.
- Config compatibility passes.
- Performance regression within budget on the reference server.
- SBOM and signed artifacts generated.
- Documentation and migration notes complete.
- No open Critical/High management-plane vulnerability without formal risk acceptance.
